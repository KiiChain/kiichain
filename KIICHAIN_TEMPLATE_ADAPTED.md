## Bug Description

**Critical vulnerability in Oracle Module price validation allowing extreme value manipulation.**

The x/oracle module's exchange rate validation only checks if values are positive (`IsPositive()`) but lacks upper bound validation. This allows validators to submit extreme exchange rates (tested up to 999,999,999,999.000000000000000000) that pass validation and influence the weighted median calculation, enabling market manipulation attacks against the entire KiiChain ecosystem.

**Affected components:**
- x/oracle/keeper/ballot.go (OrganizeBallotByDenom function)  
- x/oracle/abci.go (EndBlocker exchange rate validation)
- x/oracle/ante.go (spam prevention mechanism)

This is a critical security bug because the code allows economically dangerous values that should never be accepted as valid exchange rates.

## Steps to Reproduce

**Tested on local KiiChain node:**

1. Set up local KiiChain node with oracle module enabled
2. Create validator with sufficient stake (>10% for median influence)
3. Submit aggregate exchange rate vote with extreme value:
   ```bash
   kiichaind tx oracle aggregate-exchange-rate-vote \
     "999999999999.000000000000000000uusdt,1.0uusdc" \
     --from validator_key \
     --chain-id oro_1336-1 \
     --gas auto \
     --fees 1000oro
   ```
4. Wait for voting period to complete
5. Query oracle exchange rates: `kiichaind query oracle exchange-rates`
6. Observe that the extreme value influences the final weighted median

**Additional reproduction - Anti-spam bypass:**
1. Submit vote in block N
2. Submit another vote in block N+1 (same voting period)
3. Both transactions succeed (should be prevented)

## Expected Behavior

**Exchange rate validation should:**
- Reject values above reasonable maximum (e.g., 1,000,000)  
- Reject values below reasonable minimum (e.g., 0.00000001)
- Maintain price stability and prevent market manipulation
- Block multiple votes per validator per voting period

**According to economic logic:**
- No legitimate asset should have exchange rates in the trillions
- Oracle prices should have sensible bounds
- Weighted median should not be influenced by extreme outliers

## Actual Behavior

**Current validation in ballot.go (lines 28-30):**
```go
if !tuple.ExchangeRate.IsPositive() {
    tmpPower = 0
}
```

**Problems observed:**
1. Extreme values like `999999999999.000000000000000000` pass validation
2. These values participate in weighted median calculation  
3. Final exchange rates can be manipulated by validators with sufficient stake
4. No upper bound checking in final validation (abci.go line 114)
5. Anti-spam allows multiple votes per voting period across different blocks

**Error logs show:** No errors - extreme values are accepted as valid.

## Proposed Fix

**Tested solution implements comprehensive price validation:**

```go
// Enhanced validation function (tested)
func (k Keeper) isValidExchangeRate(rate sdk.Dec) bool {
    if !rate.IsPositive() {
        return false
    }
    
    // Configurable bounds (tested with these values)
    maxPrice := sdk.NewDecFromInt(sdk.NewIntFromUint64(1_000_000_000))
    minPrice := sdk.NewDecWithPrec(1, 8)
    
    return rate.LTE(maxPrice) && rate.GTE(minPrice)
}
```

**Applied to ballot.go:**
```go
if !k.isValidExchangeRate(tuple.ExchangeRate) {
    tmpPower = 0  // Now rejects extreme values
}
```

**Testing shows:** Extreme values now properly rejected, normal prices pass validation.
